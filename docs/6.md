# Phase 6: Embedded Go SDK

## Goal

Create a public `joydb` package inside the existing project so any Go developer can `import "github.com/leengari/joydb/joydb"` and use JoyDb as an embedded database. Supports multiple isolated databases under one root directory.

> [!IMPORTANT]
> **Not a separate project.** A new top-level `joydb/` package in the existing repo. All internals stay in `internal/`. The SDK is a thin public wrapper around the existing engine, registry, and WAL.

> [!IMPORTANT]
> **Module rename required.** `go.mod` changes from `github.com/leengari/mini-rdbms` to `github.com/leengari/joydb`. All internal `import` paths get updated accordingly. This is a mechanical find-and-replace — no logic changes.

---

## Architecture: Two-Tier API (`Store` → `DB`)

JoyDb stores data as **directories**, not single files. A `Store` is the root directory. Each named `DB` inside it is a subdirectory with its own WAL, snapshots, and tables — fully isolated.

```
./data/                    ← Store root (passed to joydb.Open)
  users_db/                ← DB named "users_db"
    wal_000001.wal
    0.snap
    meta.json
  analytics_db/            ← DB named "analytics_db" (separate WAL, separate tables)
    wal_000001.wal
    ...
```

Maps directly to the existing `Registry` (manages multiple databases) and `WALManager` (per-database WAL) architecture — zero new infrastructure needed.

## What the User Sees

```go
import "github.com/leengari/joydb/joydb"

// Open the store — root directory where all databases live
store, err := joydb.Open("./data")
defer store.Close()

// Access a database by name (creates it if it doesn't exist)
usersDB, err := store.DB("users_db")
analyticsDB, err := store.DB("analytics_db")

// DDL
usersDB.Exec("CREATE TABLE users (id INT PRIMARY KEY AUTO_INCREMENT, name TEXT, age INT)")

// Parameterized DML
usersDB.Exec("INSERT INTO users (name, age) VALUES (?, ?)", "Alice", 30)

// Query with StructScan (Simplest DX)
type User struct {
    ID   int64  `joydb:"id"`
    Name string `joydb:"name"`
    Age  int64  `joydb:"age"`
}
rows, err := usersDB.Query("SELECT id, name, age FROM users WHERE age > ?", 20)
for rows.Next() {
    var u User
    rows.StructScan(&u) // Automatically maps columns to fields via reflection/tags
    fmt.Println(u.ID, u.Name, u.Age)
}

// Transactions
tx, _ := usersDB.BeginTx(context.Background())
tx.Exec("UPDATE users SET age = 31")
tx.Commit()

// In-memory store (no files written anywhere)
// ":memory:" is the sentinel — same convention as SQLite
memStore, err := joydb.Open(":memory:")
memDB, err := memStore.DB("scratch")
```

### Phase 6.1: `Store` — The Root (`Open`, `Close`)

**One entry point.** `Open` handles both persistent and in-memory modes. If the path is `":memory:"`, no files are created or read. Same convention as SQLite, already understood by any Go developer who has used `database/sql`.

#### [NEW] `joydb/store.go`

```go
type Store struct {
    registry *manager.Registry
    basePath string        // ":memory:" means no disk I/O
}

// Open opens (or creates) a store.
//
// Persistent:   joydb.Open("./data")
// In-memory:    joydb.Open(":memory:")
//
// For persistent stores, WAL and crash recovery are enabled by default.
// Use options to tune behaviour (WithoutWAL, WithWALSyncInterval, etc.).
// Options are ignored for ":memory:" stores (nothing to persist).
func Open(path string, opts ...Option) (*Store, error)

// DB returns (or creates) a named database within this store.
// Subsequent calls with the same name return the same *DB.
func (s *Store) DB(name string) (*DB, error)

// ListDBs returns the names of all databases in this store.
func (s *Store) ListDBs() ([]string, error)

// DropDB permanently deletes a database and all its data.
func (s *Store) DropDB(name string) error

// Close flushes all WALs, writes final snapshots, and releases resources.
// For ":memory:" stores this is a no-op.
func (s *Store) Close() error
```

`Open("./data")` internally:
1. `os.MkdirAll("./data", 0755)`
2. `engine.NewMemoryEngine()`
3. `manager.NewRegistryWithWAL("./data", storageEngine, true, 5s, 0)`
4. Returns `&Store{registry, "./data"}`

The user calls `store.DB("mydb")` which internally does `registry.GetWithWAL("mydb")` — triggering WAL recovery if needed.

#### [NEW] `joydb/options.go`

Every flag exposed by the `joydb` CLI binary is also available as a functional option on `Open`/`OpenMemory`. The config has safe defaults so zero options are required.

```go
type Option func(*config)

// --- WAL Options ---

// WithoutWAL disables Write-Ahead Logging entirely.
// Data is still saved on Close(), but a crash between writes loses
// any uncommitted data since the last checkpoint.
// Maps to: --no-wal flag
func WithoutWAL() Option

// WithWALSyncInterval sets how often the WAL is fsynced to disk.
// Default (0) means fsync on every single commit — maximum durability,
// lower throughput. Set to e.g. 100ms for async batching (SQLite WAL-mode equivalent).
// Maps to: --wal-sync-interval flag
func WithWALSyncInterval(d time.Duration) Option

// WithCheckpointInterval controls how often the WAL is folded into
// the snapshot. Shorter = more frequent full saves, lower recovery time.
// Default: 5 seconds.
// Maps to: --checkpoint-interval flag
func WithCheckpointInterval(d time.Duration) Option

// --- Logging Options ---

// WithDebugLogging enables verbose structured debug logs via slog.
// Useful when debugging WAL recovery or query planning issues.
// Maps to: --debug flag
func WithDebugLogging() Option
```

Usage examples:

```go
// Maximum durability — fsync on every commit (default)
store, _ := joydb.Open("./data")

// High throughput — async WAL sync every 100ms, checkpoint every 30s
store, _ := joydb.Open("./data",
    joydb.WithWALSyncInterval(100*time.Millisecond),
    joydb.WithCheckpointInterval(30*time.Second),
)

// No WAL — fastest possible, loses uncommitted data on crash
store, _ := joydb.Open("./data",
    joydb.WithoutWAL(),
)

// Debug mode to trace query planning and WAL operations
store, _ := joydb.Open("./data",
    joydb.WithDebugLogging(),
)

// In-memory — options are silently ignored (nothing to persist)
store, _ := joydb.Open(":memory:")
```

Internally, `config` is a private struct with these defaults:

```go
type config struct {
    walEnabled         bool          // true
    walSyncInterval    time.Duration // 0 (sync on commit)
    checkpointInterval time.Duration // 5 * time.Second
    debug              bool          // false
}
```

#### Verification
- `Open` → `DB("x")` → `DB("y")` → `ListDBs()` returns `["x", "y"]`
- `Close` → re-`Open` → data survives (WAL recovery fires)
- `Open(":memory:")` → full CRUD cycle → no files created on disk

### Phase 6.2: `DB` — Query Execution (`Exec`, `Query`)

#### [NEW] `joydb/db.go`

```go
type DB struct {
    name    string
    engine  *engine.Engine
    schema  *schema.Database
    mu      sync.RWMutex // Thread-safety: *DB is safe for concurrent use by multiple goroutines.
}

// Exec runs a SQL statement. Wraps ExecContext(context.Background()).
func (db *DB) Exec(sql string, args ...interface{}) (ExecResult, error)
func (db *DB) ExecContext(ctx context.Context, sql string, args ...interface{}) (ExecResult, error)

// Query runs a SQL SELECT and returns an iterable *Rows. Wraps QueryContext(context.Background()).
func (db *DB) Query(sql string, args ...interface{}) (*Rows, error)
func (db *DB) QueryContext(ctx context.Context, sql string, args ...interface{}) (*Rows, error)

// BeginTx starts a new transaction.
func (db *DB) BeginTx(ctx context.Context) (*Tx, error)
```

Both `Exec` and `Query` call the same `engine.Execute()` under the hood. 
Each call to `Exec`/`Query` without an explicit transaction is automatically wrapped in an internal transaction.

> [!NOTE]
> **Implementation Note (Engine API):** To support the `tx.Exec` and `tx.Query` methods below, the internal `Engine` needs to be refactored to support passing an explicit transaction. Currently, `engine.Execute(sql)` automatically creates its own transaction. We will add `engine.ExecuteTx(tx, sql, args)` so the SDK can decouple transaction management from query execution.

### Phase 6.3: Parameterized Queries (`?` Placeholders)

**Goal**: Prevent SQL injection by safely interpolating args before passing to the parser.

#### [NEW] `joydb/params.go`

A single `interpolate(sql string, args []interface{}) (string, error)` function.

Type mapping:
| Go type | SQL literal |
|---|---|
| `int`, `int32`, `int64` | `42` |
| `float32`, `float64` | `3.14` |
| `string` | `'Alice'` (internal `'` → `''`) |
| `bool` | `TRUE` / `FALSE` |
| `nil` | `NULL` |
| anything else | error |

Returns an error if the count of `?` markers doesn't match the count of `args`.

This is **client-side interpolation** — safe for an embedded DB because there is no network boundary. The "client" and "server" are the same process. Same approach as SQLite's `sqlite3_mprintf`.

> [!CAUTION]
> **Implementation Note (Interpolation Flaw):** Naive string interpolation (e.g. `strings.Replace`) is actually extremely dangerous and broken. If a user runs `Exec("SELECT * FROM users WHERE notes = 'Who is this?' AND age = ?", 25)`, replacing `?` blindly will corrupt the query by injecting the parameter *inside* the string literal. 
> Instead of `interpolate(sql, args)`, we will implement parameterization at the **AST Level**. The Lexer will emit a token for `?`, the Parser will create an `ast.ParameterExpression`, and the Execution Engine will evaluate it against the `args` slice. This guarantees 100% safety.

#### Verification
- `"INSERT INTO t VALUES (?, ?)", "O'Brien", 42` → `"INSERT INTO t VALUES ('O''Brien', 42)"`
- `"SELECT * FROM t WHERE active = ?", true` → `"SELECT * FROM t WHERE active = TRUE"`
- `"SELECT * FROM t WHERE val = ?", nil` → `"SELECT * FROM t WHERE val = NULL"`
- Wrong arg count → error

### Phase 6.4: Typed Row Results (`*Rows` Iterator)

#### [NEW] `joydb/rows.go`

```go
type Rows struct {
    columns  []string           // column names in order
    metadata []ColumnMetadata   // column types (INT, TEXT, FLOAT, BOOL)
    data     []data.Row         // raw rows from executor
    cursor   int                // current position
    colIndex map[string]int     // column name → index for named accessors
}

// Next advances to the next row. Returns false when exhausted.
func (r *Rows) Next() bool

// Scan copies the current row's values into the provided pointers.
// Supports *int64, *float64, *string, *bool, *interface{}.
// Returns error if dest count != column count, or type is incompatible.
func (r *Rows) Scan(dest ...interface{}) error

// StructScan populates a struct using reflection, matching column names to fields or `joydb` tags.
func (r *Rows) StructScan(dest interface{}) error

// Columns returns the ordered list of column names.
func (r *Rows) Columns() []string

// Close is a no-op (satisfies database/sql-like convention).
func (r *Rows) Close() error
```

Convenience accessors (look up by column name, no Scan needed):
```go
func (r *Rows) String(col string) string
func (r *Rows) Int(col string) int64
func (r *Rows) Float(col string) float64
func (r *Rows) Bool(col string) bool
func (r *Rows) IsNull(col string) bool
func (r *Rows) Value(col string) interface{}  // raw value
```

`Scan` type coercion rules:
- Column is `int64`, dest is `*int` → convert
- Column is `float64`, dest is `*int64` → truncate
- Column is `string`, dest is `*int64` → attempt `strconv.ParseInt`, error if fails
- Any column, dest is `*interface{}` → pass through as-is
- `StructScan` attempts to map column names (e.g. `user_id`) to struct tags (`joydb:"user_id"`) or field names (`UserId`).

#### Verification
- `Scan` with correct types — all values populated
- `Scan` with `*interface{}` — raw values pass through
- `Scan` with wrong dest count — error returned
- `rows.String("name")` on non-existent column — returns zero value, no panic
- `rows.Next()` after exhaustion — returns `false`, no panic
