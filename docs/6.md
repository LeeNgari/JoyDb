# Phase 6: Embedded Go SDK

## Goal

Create a public `joydb` package so any Go developer can import JoyDb and use it as an
embedded database, with a `Store` → `DB` API, typed row scanning, safe parameters, and
transactions. Supports multiple isolated databases under one root directory.

**Status: Complete (2026-07-10).** All Phase 6 milestones below are implemented and verified.

> [!IMPORTANT]
> **Not a separate project.** A new public package in the existing repo. All internals stay
> in `internal/`. The SDK is a thin public wrapper around the existing engine, registry, and WAL.

> [!IMPORTANT]
> **Public package placement:** the SDK is exposed at the module root, so applications import
> `github.com/leengari/joydb` without `joydb/joydb` stutter.

---

## Reality check (verified against current code — 2026-07-10)

This plan was audited against the codebase. The `Store` → `DB` architecture, functional
options, and typed `Rows` scanning are well-supported. Four items were **underestimated or
missing infrastructure** and have been re-scoped below. Read this before starting.

| Advertised feature | Code reality | Verdict |
|---|---|---|
| `Store`/`DB` over `Registry` + per-DB WAL | `manager.NewRegistryWithWAL(...)` exists with checkpoint/sync intervals | ✅ Solid foundation |
| `Rows` / `Scan` / `StructScan` | `executor.Result` already carries `Columns []string` and `Metadata []ColumnMetadata{Name, Type}` | ✅ Easiest win |
| `ExecResult.RowsAffected()` | `executor.Result.RowsAffected` exists | ✅ Direct map |
| `store.DB(name)` "creates if missing" | `registry.GetWithWAL` calls `storageEngine.LoadDatabase(dbPath)`, which **errors** if the dir is absent — there is no create-on-open path | ⚠️ Must add create-on-open |
| `ExecResult.LastInsertID()` | `executor.Result` has **no** `LastInsertID` field; `Table.LastInsertID` exists internally but is never surfaced | ⚠️ Plumbing required |
| Typed errors (`ErrTableNotFound`, …) | Engine returns `fmt.Errorf("table not found: %s", …)` strings; no sentinels for `errors.Is` | ⚠️ Mapping layer required |
| `?` parameters | **No `?` token** in the lexer, no `ast.ParameterExpression`, no evaluator. The "interpolate" approach is self-contradicted by the plan's own CAUTION note | 🔴 Full pipeline feature |
| `:memory:` mode | `MemoryEngine` is a **disk snapshot** engine (misnomer): `LoadDatabase` stats disk, `CreateDatabase` does `os.MkdirAll`, WAL writes files. No RAM-only path exists | 🔴 New `StorageEngine`, not a sentinel |
| `BeginTx`/`Commit`/`Rollback` + `ctx` | `engine.Execute` **always** creates and closes its own transaction (auto-commit). No external-tx passing, no interactive multi-statement tx, no rollback of applied statements, isolation only via table-level `RWMutex`. `ctx` is not plumbed anywhere | 🔴 Largest item; depends on Phase 5 row-level locking |

## Architecture: Two-Tier API (`Store` → `DB`)

JoyDb stores data as **directories**, not single files. A `Store` is the root directory. Each
named `DB` inside it is a subdirectory with its own WAL, snapshots, and tables — fully isolated.

```
./data/                    ← Store root (passed to Open)
  users_db/                ← DB named "users_db"
    wal_000001.wal
    0.snap
    meta.json
  analytics_db/            ← DB named "analytics_db" (separate WAL, separate tables)
    wal_000001.wal
    ...
```

Maps directly to the existing `Registry` (manages multiple databases) and `WALManager`
(per-database WAL) architecture — zero new infrastructure needed for the persistent path.

## What the User Sees (target end state)

```go
import "github.com/leengari/joydb"

// Open the store — root directory where all databases live
store, err := joydb.Open("./data")
defer store.Close()

// Access a database by name (creates it if it doesn't exist)
usersDB, err := store.DB("users_db")

// DDL
usersDB.Exec("CREATE TABLE users (id INT PRIMARY KEY AUTO_INCREMENT, name TEXT, age INT)")

// Parameterized DML (AST-bound, not string interpolation)
usersDB.Exec("INSERT INTO users (name, age) VALUES (?, ?)", "Alice", 30)

// Query with StructScan (simplest DX)
type User struct {
    ID   int64  `joydb:"id"`
    Name string `joydb:"name"`
    Age  int64  `joydb:"age"`
}
rows, err := usersDB.Query("SELECT id, name, age FROM users WHERE id > ?", 20)
for rows.Next() {
    var u User
    rows.StructScan(&u)
    fmt.Println(u.ID, u.Name, u.Age)
}

// Transactions
tx, _ := usersDB.BeginTx(context.Background())
tx.Exec("UPDATE users SET age = 31 WHERE id = ?", 1)
tx.Commit()

// In-memory store
memStore, err := joydb.Open(":memory:")
memDB, err := memStore.DB("scratch")
```

The complete API above is implemented. Transactions currently provide serialized isolation:
one transaction owns its `DB` handle until `Commit` or `Rollback`.

### Phase 6.1: `Store` — The Root (`Open`, `Close`, `DB`) ✅

- [x] Complete

**One entry point.** `Open` handles persistent paths and routes `":memory:"` to the true
in-memory storage engine implemented in Phase 6.6.

> [!IMPORTANT]
> **Create-on-open is the key fix.** `registry.GetWithWAL(name)` errors when the database
> directory does not exist (`LoadDatabase` → `os.Stat` fails). `store.DB(name)` must:
> 1. Try `registry.GetWithWAL(name)`.
> 2. If it fails because the DB is absent, call `registry.Create(name)` (which `MkdirAll`s
>    the directory) and retry `GetWithWAL`.
> 3. Cache the resulting `*DB` so repeated calls return the same handle.
> Without this, `DB("users_db")` fails on a fresh store.

#### [NEW] public `store.go`

```go
type Store struct {
    registry *manager.Registry
    basePath string
    mu       sync.Mutex
    dbs      map[string]*DB // handle cache
}

// Open opens (or creates) a persistent store rooted at path.
// path == ":memory:" creates a RAM-only store.
func Open(path string, opts ...Option) (*Store, error)

// DB returns (or creates) a named database within this store.
// Creates the database directory on first access; caches the handle.
func (s *Store) DB(name string) (*DB, error)

func (s *Store) ListDBs() ([]string, error)
func (s *Store) DropDB(name string) error
func (s *Store) Close() error // flush WALs, final snapshots, release resources
```

`Open("./data")` internally:
1. `os.MkdirAll("./data", 0755)`
2. `engine.NewMemoryEngine()`
3. `manager.NewRegistryWithWAL("./data", storageEngine, walEnabled, checkpointInterval, syncInterval)`
4. Returns `&Store{registry, "./data", …}`

#### Verification
- `Open` → `DB("x")` on a **fresh** store succeeds (create-on-open).
- `DB("x")` twice returns the same cached handle.
- `Open` → `DB("x")` → `DB("y")` → `ListDBs()` returns `["x", "y"]`.
- `Close` → re-`Open` → data survives (WAL recovery fires).
- `Open(":memory:")` performs full CRUD without filesystem access.

### Phase 6.2: Typed Row Results (`*Rows` Iterator) ✅

- [x] Complete

Do this early: it is the biggest DX win and is fully supported by existing internals.
`executor.Result` already exposes `Columns []string` and `Metadata []ColumnMetadata{Name, Type}`.

#### [NEW] public `rows.go`

```go
type Rows struct {
    columns  []string
    metadata []executor.ColumnMetadata // Name + Type (INT/TEXT/FLOAT/BOOL)
    data     []data.Row
    cursor   int
    colIndex map[string]int
}

func (r *Rows) Next() bool
func (r *Rows) Scan(dest ...interface{}) error       // *int64, *float64, *string, *bool, *interface{}
func (r *Rows) StructScan(dest interface{}) error     // reflection: `joydb` tag or field name
func (r *Rows) Columns() []string
func (r *Rows) Close() error                          // no-op, database/sql-style
```

Convenience accessors (look up by column name, no `Scan` needed):
```go
func (r *Rows) String(col string) string
func (r *Rows) Int(col string) int64
func (r *Rows) Float(col string) float64
func (r *Rows) Bool(col string) bool
func (r *Rows) IsNull(col string) bool
func (r *Rows) Value(col string) interface{}
```

`Scan` coercion: `int64`→`*int`, `float64`→`*int64` (truncate), `string`→`*int64`
(`strconv.ParseInt`, error on fail), any→`*interface{}` pass-through. `StructScan` maps
column names to `joydb:"…"` tags or exported field names.

#### Verification
- `Scan` with correct types populates all values.
- `Scan` with `*interface{}` passes raw values through.
- `Scan` with wrong dest count returns an error.
- `rows.String("nope")` on a missing column returns zero value, no panic.
- `rows.Next()` after exhaustion returns `false`, no panic.

### Phase 6.3: `DB` — Query Execution (`Exec`, `Query`, auto-commit) ✅

- [x] Complete

`Exec` and `Query` route through auto-commit execution. Interactive transactions use the
caller-owned execution path implemented in Phase 6.7.

#### [NEW] public `db.go`

```go
type DB struct {
    name   string
    engine *engine.Engine
    schema *schema.Database
    mu     sync.RWMutex // safe for concurrent use; serializes access for now
}

func (db *DB) Exec(sql string, args ...interface{}) (ExecResult, error)
func (db *DB) Query(sql string, args ...interface{}) (*Rows, error)
```

`ExecContext` and `QueryContext` propagate cancellation through lexer, parser, planner, and
execution stage boundaries.

> [!NOTE]
> **One engine per `DB`.** `engine.Execute` is stateful (`e.db`, `e.walManager` set by the
> SQL `USE` path). Each `*DB` must own an engine already bound to its database + WAL manager
> and must **not** rely on `USE`. `Store` — not SQL — owns database lifecycle.

#### [NEW] public `result.go` — **requires internal plumbing**

```go
type ExecResult struct {
    rowsAffected int64
    lastInsertID int64
}

func (r ExecResult) RowsAffected() int64
func (r ExecResult) LastInsertID() int64
```

> [!IMPORTANT]
> `executor.Result` currently has **no** `LastInsertID` field. Add one, populate it from
> `Table.LastInsertID` in the insert executor/result formatter, and surface it through the
> engine so `ExecResult.LastInsertID()` is meaningful. Without this, it always returns 0.

#### [NEW] public `errors.go` — **requires a mapping layer**

```go
var ErrTableNotFound     = errors.New("joydb: table not found")
var ErrUniqueConstraint  = errors.New("joydb: unique constraint violation")
// … other common errors
```

The engine returns formatted strings today. Add a translation layer (public API boundary)
that maps internal errors — including the existing `internal/domain/errors` constraint
types — onto these sentinels so callers can use `errors.Is`.

#### Verification
- `Exec("CREATE TABLE")` → no error.
- `Exec("INSERT …")` → `RowsAffected() == 1`.
- `Exec("INSERT …")` on an auto-increment table → `LastInsertID()` returns the new id.
- `Query("SELECT …")` on a missing table → `errors.Is(err, ErrTableNotFound)` is true.

### Phase 6.4: Functional Options (WAL / logging config) ✅

- [x] Complete

Maps directly onto the parameters of `NewRegistryWithWAL`. Safe defaults so zero options
are required.

```go
type Option func(*config)

func WithoutWAL() Option                          // walEnabled = false
func WithWALSyncInterval(d time.Duration) Option  // 0 = fsync on commit
func WithCheckpointInterval(d time.Duration) Option // default 5s
func WithDebugLogging() Option                    // verbose slog

type config struct {
    walEnabled         bool          // true
    walSyncInterval    time.Duration // 0 (sync on commit)
    checkpointInterval time.Duration // 5 * time.Second
    debug              bool          // false
}
```

Usage:
```go
store, _ := joydb.Open("./data") // durable defaults
store, _ := joydb.Open("./data",
    joydb.WithWALSyncInterval(100*time.Millisecond),
    joydb.WithCheckpointInterval(30*time.Second),
)
store, _ := joydb.Open("./data", joydb.WithoutWAL())
```

#### Verification
- Options flow into `NewRegistryWithWAL` and change observable behaviour (e.g. `WithoutWAL`
  produces no WAL files).

### Phase 6.5: Parameterized Queries (`?`) — AST-level binding ✅

- [x] Complete

**Goal**: SQL-injection-safe parameters. This is a pipeline feature, **not** string
interpolation — the original "interpolate" idea is dropped because it corrupts string
literals (e.g. `WHERE notes = 'Who is this?' AND age = ?`).

Required changes across the pipeline:
1. **Lexer** — emit a new `QUESTION` token for `?` (no such token exists today).
2. **AST** — add `ast.ParameterExpression{Index int}`.
3. **Parser** — accept `?` anywhere a literal/value is valid; assign ordinal indices.
4. **Binding** — before/at execution, substitute each `ParameterExpression` with the typed
   value from `args` (typed value, not text), validating arg count and type.
5. **Public API** — `Exec`/`Query` forward `args` through the engine to the binder.

Type mapping for bound values: `int/int32/int64`→INT, `float32/float64`→FLOAT,
`string`→TEXT, `bool`→BOOL, `nil`→NULL, anything else → error. Mismatched `?`/arg counts → error.

#### Verification
- `Exec("INSERT INTO t VALUES (?, ?)", "O'Brien", 42)` inserts `O'Brien`, `42` with no
  corruption of the literal.
- `Query("SELECT * FROM t WHERE notes = 'a?b' AND id = ?", 1)` treats `?` inside the string
  literal as literal text, and binds only the real placeholder.
- Wrong arg count → error.

### Phase 6.6: In-Memory Mode (`:memory:`) ✅

- [x] Complete

**Not a sentinel branch — new infrastructure.** `MemoryEngine` is misnamed; it persists to
disk (snapshots + WAL files). `:memory:` requires a genuine RAM-only path.

Approach (pick one, document the choice):
- **Option A** — a new `StorageEngine` implementation (e.g. `RAMEngine`) whose
  `LoadDatabase`/`SaveDatabase`/`CreateSnapshot` operate on in-memory structures and never
  touch the filesystem, wired with WAL disabled.
- **Option B** — a `:memory:` flag threaded through the registry that skips `MkdirAll`,
  snapshot load/save, and WAL creation entirely.

Either way, `Open(":memory:")` must create/read **no** files, ignore persistence options,
and support the full CRUD cycle in RAM.

#### Verification
- `Open(":memory:")` → `DB("scratch")` → full CRUD → `os.Stat` on any candidate path fails
  (nothing written to disk).
- Two in-memory DBs in one store remain isolated.

### Phase 6.7: Transactions (`BeginTx` / `Commit` / `Rollback`) ✅

- [x] Complete

Transactions use a caller-owned engine execution path and one buffered WAL transaction.
They currently hold the `DB` write lock for their lifetime and keep a deep table snapshot for
rollback. This provides atomic, serialized isolation now; Phase 5 row-level locking remains a
future throughput optimization rather than a correctness dependency.

Required work:
1. **Engine** — add `engine.ExecuteTx(tx, sql, args)` so a statement runs inside a
   caller-owned transaction instead of a per-call one.
2. **Transaction lifecycle** — buffer changes and support `Rollback()` that discards applied
   effects (WAL abort path exists for aborts; extend to interactive use).
3. **Isolation** — depends on Phase 5 row/table locking; document the guarantee actually
   provided (initially likely serialized via the `DB` mutex).
4. **Context** — plumb `ctx` for cancellation/timeout and add `ExecContext`/`QueryContext`/
   `BeginTx(ctx)`.

```go
type Tx struct { /* caller-owned transaction state */ }

func (db *DB) BeginTx(ctx context.Context) (*Tx, error)
func (tx *Tx) Exec(sql string, args ...interface{}) (ExecResult, error)
func (tx *Tx) Query(sql string, args ...interface{}) (*Rows, error)
func (tx *Tx) Commit() error
func (tx *Tx) Rollback() error
```

#### Verification
- `BeginTx` → two `Exec`s → `Rollback()` → neither change is visible.
- `BeginTx` → `Exec`s → `Commit()` → changes persist and survive reopen.
- A cancelled `ctx` aborts an in-flight transaction.

## Out-of-scope gaps that still hurt "easy to use"

Not part of Phase 6, but users of an embedded DB will expect these. Flagged here (and worth
adding to [roadmap.md](roadmap.md) / [todos.md](todos.md)) because they shape first
impressions even after the SDK ships:

- **GROUP BY** — lexer tokens exist, but there is **no parser/planner/executor execution
  path** for grouped aggregation. Aggregates currently work only ungrouped. Users will
  expect `SELECT dept, COUNT(*) FROM emp GROUP BY dept`.
- **Index use is primary-key only** — the planner emits an `IndexScanNode` only for PK
  predicates; a `WHERE` on any **secondary column falls back to a full sequential scan**.
  Secondary/ B+Tree indexes on non-PK columns would be expected for an "easy, fast" DB.
- **Prepared-statement reuse** — even after Phase 6.5 adds `?` binding, there is no
  `Prepare()`/reusable statement handle. Every call re-lexes/re-parses/re-plans. A
  `db.Prepare(sql)` returning a reusable `*Stmt` is a common expectation and a real
  performance lever for hot paths.
