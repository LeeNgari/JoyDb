# Phase 5.3: Array-Based Row Storage Transition

This document outlines the architectural shift from `map[string]interface{}` to `[]interface{}` for core `data.Row` storage. This change will eliminate map allocation overhead and drastically improve full table scan throughput.

> [!WARNING]
> **Breaking Change**: The binary serialization format of rows on disk will change. The WAL JSON format will change from objects (`{"id": 1}`) to arrays (`[1]`). Since JoyDb is a toy database, we will prioritize performance over backward compatibility for old WAL files.

## Proposed Changes

The refactor is broken down into four isolated phases to maintain testability at each step.

---

### Phase 1: Core Data & Schema Models

**Goal**: Prepare the schema to provide fast index lookups and change the fundamental `Row` structure.

#### [MODIFY] `internal/domain/schema/table_schema.go`
- Add `GetColumnIndex(name string) int` to map column string names to integer indexes efficiently.

#### [MODIFY] `internal/domain/data/row.go`
- Change `Row` struct: `Data map[string]interface{}` -> `Values []interface{}`.
- Change `Copy()` to use built-in `copy()` on slices.
- Change `MarshalJSON` and `UnmarshalJSON` to handle JSON arrays instead of objects.
- Change `Serialize` and `Deserialize` binary format to completely drop `KeyLen` and `Key` bytes, storing only the sequential values.

---

### Phase 2: Insert, Update, and Base Table Operations

**Goal**: Ensure we can safely create, read, update, and delete the new `Row` objects.

#### [MODIFY] `internal/domain/schema/table.go`
- Update `Insert`, `Update`, and `Delete` logic where `row.Data["id"]` is currently used to manage Primary Keys. It must now use the PK index from the schema.
- Update `LiveRowsUnsafe()` and `ForEachLiveRowUnsafe()` to return slices without deep-copying strings.

#### [MODIFY] `internal/executor/insert_executor.go`
- Currently, `InsertNode` provides a `map[string]interface{}`. The executor must map these key-value pairs into a correctly ordered `[]interface{}` using `table.Schema` before inserting.

#### [MODIFY] `internal/executor/update_executor.go`
- Convert incoming `SET` maps into targeted index updates within the `Row.Values` array.

#### [MODIFY] `internal/validation/row_validator.go`
- Refactor the validator to iterate over `Row.Values` rather than map keys.

---

### Phase 3: Planner & Predicates (The Brain)

**Goal**: Change how JoyDb evaluates `WHERE` clauses.

#### [MODIFY] `internal/planner/predicate/builder.go`
- Change `Build(expr ast.Expression)` to `Build(expr ast.Expression, tSchema *schema.TableSchema)`.
- When building a comparison (`age > 25`), resolve the column name `age` to an index (e.g., `2`) during *planning time*.
- The returned `func(data.Row) bool` closure will capture this index and execute `row.Values[2] > 25` during *execution time*.

#### [MODIFY] `internal/planner/planner.go`
- Update all calls to `predicate.Build` to pass the target table's schema.

#### [MODIFY] `internal/query/indexing/builder.go`
- Update B+Tree index builders to extract keys using integer indexes instead of map string lookups.

---

### Phase 4: WAL and Join Integration

**Goal**: Fix the periphery. To limit the blast radius, **Joins will continue to use temporary Maps (`JoinedRow`)**.

#### [MODIFY] `internal/storage/manager/wal_manager.go`
- Update the crash-recovery parser to unmarshal JSON arrays instead of JSON objects.
- Map the array values back to their columns using the loaded Table Schema.

#### [MODIFY] `internal/executor/select_executor.go`
- When passing a base `Row` to the `projection` engine or `Join` engine, temporarily construct a `JoinedRow{Data: map...}` using the `TableSchema`. This isolates the `[]interface{}` optimization to the base table scans while keeping Joins untouched for now.

---

## Verification Plan

### Automated Tests
- Run `go test ./...`
- Verify that `WAL` recovery works with the new JSON array format.

### Benchmark Verification
- Run `go run ./cmd/bench --label phase5.3 --duration 5s`
- **Expected Outcome**: `select_full_scan_10k` should jump from ~160 TPS to thousands of TPS. `select_full_scan_1k` should increase from ~1,500 TPS to >20,000 TPS.
